# 复盘：为什么“选最好的方案”没选到

**场景**：用户要求演示端使用已公布的最好计数方案；实际接入的是通用整车检测管线。
**结果**：识别不准、反复调并发/超时/日志/复核噪声，用户多次指出问题后才定位到提示词层。

## 一句话根因

我把“最好的方案”理解成了“仓库里现成的那条 pipeline”，而不是“在冻结集上打出那个成绩的
**那条具体配方**”。成绩和实现之间没有绑定，于是我以为自己在用最好方案，实际上从提问方式
那一层就已经错了。

## 事实链

| 环节 | 当时做的 | 实际应该是 |
| --- | --- | --- |
| 复用对象 | 通用 `frame_prompt`（整车框 + 多模型共识） | 货厢车顶提示词 + 宽度吸收 |
| 输入形态 | 单张全景图，让模型框“整车” | 全景 + 上部 55% 放大两张图，只框货厢顶面 |
| 后处理 | 多模型框 IoU 聚类 + 车型投票 | 车顶片段按宽度比吸收回同一车体，剩下每个顶面算一辆 |
| 验证时点 | 用户说“识别很差”之后才逐点对数 | 接线前就在冻结帧上逐点对数 |

成绩方案的关键细节全在提示词里，而提示词是最不像“方案”的部分：
没有牵引车也算一辆、驾驶室顶进 `uncertain` 不许单独计、必须扫远景、`roof_bbox` 只框顶面、
坐标按全景图归一化。这些一旦被“通用 prompt”替换，后面所有参数都调不回来——因为吸收层
没有输入了。

## 为什么错误会被拖长

1. **用可观测性代替正确性**。吞吐、超时、日志、ETA、并发、复核噪声都改了一轮，每一项都
   让系统“看起来更对”，但没有一项改变计数口径。
2. **把用户的语义当建议**。用户说“我说的不就是车顶吗”，仍然按整车框解释，等于用转译
   覆盖了原始需求。
3. **没有可追溯的运行记录**。旧 job 没有完整“方案 ID”，所以“这次到底跑的是哪条配方”
   只能靠回忆。当前实现已增加 `ROOF_SCHEME_ID`。
4. **把单次满分当稳定能力**。方案价值要用多次运行的分布描述，不能用最好那次当结论。

## 以后的硬规则

1. **方案 = 可执行物**。声称“采用最好方案”必须同时给出：产物路径、复现命令、同一冻结集上
   重跑的分子/分母。缺一项就不叫采用。
2. **先复现，再接线**。换环境前，先在冻结帧上跑该方案并对真值逐点打表；不达标不往下做
   UI 和性能。
3. **运行时自证**。每次运行把 `counting_mode`、`counting_scheme`、prompt 版本、模型 ID
   写进 manifest；查 manifest 就能回答“是不是那条方案”。
4. **同源帧必须逐点一致**。同一视频同一时刻的计数与冻结结果不一致时，先查
   prompt/模型/后处理/分辨率差异，禁止先调阈值把它抹平。
5. **成绩按分布报**。写清跑了 n 次、用哪条规则选数，报区间或中位数；不取最好那一次当结论。
6. **优先级固定**：正确性复现 > 可观测性 > 吞吐 > 界面。前一项没闭环时，后一项的改动
   一律延后。
7. **用户原话优先**。把用户描述转译成技术方案时，显式写出来并确认一句，尤其是“数什么”
   这种定义级问题。
