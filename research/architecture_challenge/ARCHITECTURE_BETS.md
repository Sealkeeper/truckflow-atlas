# 架构下注记录：货车计数

日期：2026-10-21

分支：`research/architecture-challenge`

范围：`north_300`、`north_600`、`south_600`、`north_1200`、`south_1200`

## 0. 结论先行

这一轮不是“找到了一个可以上线的通用算法”，而是明确了几条**有条件成立**的路线：

- **保留并进入 20 帧回归**：紧贴通道的纵向深度窗口（A′）+ 迭代式语义去重。
- **仅保留为关系先验**：场景图的 `lane_id` / `queue_index` / `part_of`，不单独计数。
- **不保留为独立架构**：递归候选树（B）和整帧后置审稿（D）。它们没有超过整帧基线；B 的 token 与 wall 约为 A′ 的 2 倍，准确率反而更低。
- **A 的宽条带**只适合作为取证/候选生成器，不适合作为自动总数。

主评测真值已切换为人工复核导出：
`all-sessions-can-see/accuracy/reviewed/user-final-review-v2-2026-10-21.json`。
该文件只提供每个机位的总车数，不提供大/中/小型拆分；因此本轮可以声称的是
**五帧诊断集上的“总数 exact / MAE / 漏计 / 多计”**，不能声称人工车型准确率。

此前 `camera_counts_v0.json` 是 AI 单人初标，只能作为车型和边界问题的诊断标签。
例如 `south_600` 的人工总数为 4，v0 为 5。任何把 v0 当作验收真值的表格都应当撤回。

## 1. 共同约束与判定口径

1. 不使用 YOLO、OpenCV 检测、跟踪或模板匹配。
2. PIL 只负责裁剪、放大、画框、坐标映射和重叠候选；这些几何量只产生“请模型判断”的候选对，不直接决定合并或车型。
3. 所有影响最终计数的语义判断都调用多模态模型；完整 prompt、原始回答、reasoning、usage、延迟和失败记录都保存在 `runs/`。
4. 牵引车 + 挂车算一辆；只看到独立运输挂车/货厢也算一辆。
5. 没有人工车型真值时，`large/medium/small` 只报告模型分布，不能把它包装成已验收字段。

## 2. 路线 A：透视深度条带

### 假设

远端车辆在画面中的尺度明显小于近端车辆。按透视缩短的 `far / upper / mid / near`
四条横带切图，并让每条带只拥有中心落在自己 core 内的候选，可以避免“整帧只看到中间大车”。

### 实现

`src/arch_bands.py`。每条带使用归一化 bbox，带间有上下文重叠，但 core 不重叠；
最后仍由共享的 `fusion.dedupe_candidates` 做跨窗语义去重。

### 实测证据

| 指标 | 结果 |
|---|---:|
| 五帧总数 | 4, 4, 4, 2, 6 |
| 人工总数 | 3, 4, 4, 3, 5 |
| 总数 exact | 2 / 5 |
| Count MAE | 0.600 |
| 漏计 / 多计 | 1 / 2 |
| 调用 / token / wall | 48 / 129,196 / 417.2 s |

`north_600` 能到 4，说明条带确实把远端两节蓝色货厢带进了视野；但 `north_300`
多 1，`north_1200` 少 1，`south_1200` 多 1，说明条带宽度和 core 边界仍会
把相邻车体切开或重复。宽条带会把展台墙、叉车和背景带入候选，之前 smoke 中
宽 `row_a` 产生 3–5 个候选，而紧贴货厢行的裁剪在两个重复样本中都给出了
灰/蓝两节不同箱体。

### 下注结论

**降级为候选生成器**。如果 20 帧回归中 A′ 失效，可以把 A 的 far 条带作为
补充取证；不要把 A 的条带总和直接作为自动总数。

## 3. 路线 A′：紧贴通道的纵向窗口

### 假设

失败不是“模型不认识货车”，而是取景不对：远端两节集装箱在宽裁剪里被展台、
立柱和队列连成一体。让窗口沿通道深度排列，far 窗口只覆盖货厢行并用“逐节枚举”
提示，mid/near/bottom 只拥有自己的深度 core，可以同时保住远端两节和近景整车。

### 实现

`src/arch_windows.py`：

- `far_b`：`x=0.39–0.57, y=0.14–0.42`，货厢行专用提示；
- 之后是 `mid / near / bottom`，中心点决定归属；
- 解析失败自动重试一次；
- 跨窗候选先做迭代式语义去重，再做车型复核。

### 实测证据

| 指标 | 结果 |
|---|---:|
| 五帧总数 | 3, 4, 5, 3, 5 |
| 人工总数 | 3, 4, 4, 3, 5 |
| 总数 exact | **4 / 5** |
| Count MAE | **0.200** |
| 漏计 / 多计 | **0 / 1** |
| 调用 / token / wall | 51 / 143,325 / 544.1 s |
| v0 诊断 full exact | 3 / 5 |

关键证据：

- `evidence/windows/north_600/final_annotated.jpg`：4 个框，远端蓝色上下两节被分别框出；
- `evidence/windows/north_300/final_annotated.jpg`：迭代去重后从 4 降为人工 3；
- `evidence/windows/south_1200/final_annotated.jpg`：总数从旧版 6 修正到人工 5。

剩余错误在 `south_600`：输出 5，人工 4。标注图里可以看到一个红色车头（框 3）
与一个同时覆盖灰色货厢和红色车头的框（框 4）；模型把“车头”和“车头+货厢”
当成不同物理车辆。这不是远端尺度问题，而是**跨窗车头/挂车关系**没有解掉。

### 成本

平均约 10.2 次调用、28.7k token、109 s/帧（本机顺序调用）。相对整帧基线约
3.6k token、16 s/帧，分别约 7.8 倍 token 和 6.9 倍 wall；这是为了恢复远端
小目标付出的可测代价，不是“免费准确率”。

### 下注结论

**保留，进入 20 帧回归。** 但必须带三个门槛：

1. 20 帧人工总数 exact 至少 17/20，MAE ≤ 0.25；
2. 不能把现有南机位多计扩大；`south_600` 的 +1 必须定位并消除；
3. 平均 wall 在可接受范围内（建议 ≤ 90 s/帧；若批量并发可另测吞吐）。

未达到任一条，就只保留 far 窗口作为取证工具，自动总数回到整帧基线。

## 4. 共享机制：迭代式语义去重

这不是一条独立架构，而是 A/A′/B/C 共用的关键修复。旧实现把所有候选对排一次序，
一旦某个候选已经并入其他候选，就跳过所有涉及它的新对；这会让“mid+near”先合并，
而“bottom”作为第三个碎片再也没有机会被送上模型。`north_300` 因此多 1。

新实现：

1. 几何只提出候选对；
2. 对每一对调用多模态 A/B 判定；
3. 合并后重新计算存活候选的框和邻近关系，最多再跑两轮；
4. 不同窗口的上下相邻框也会被提出，但仍由模型判断是同一辆车还是两辆车。

这项修复使 A′ 的五帧从旧版 `4,4,4,3,6`（3/5 exact，MAE 0.40）变为
`3,4,5,3,5`（4/5 exact，MAE 0.20）。净收益来自 `north_300` 和 `south_1200`，
但 `south_600` 从 4 变成 5，说明“提出更多相邻对”也会把模型的错误判定放大。
因此下一轮需要的是**同一对的多视图复核/一致票**，而不是继续加几何阈值。

## 5. 路线 B：递归区域树

### 假设

先让模型提出可能有车的区域，再对可疑子区域递归放大；子节点的 core 取代父节点
在该区域的候选，既能找回被遮挡车辆，又能避免整帧漏计。

### 实现

`src/arch_tree.py`。根节点由 `region_proposal_prompt` 产生，每个节点最多 8 个；
子节点通过 `suspect_subregions` 递归，父候选在子 core 内被 supersede。

### 实测证据

| 指标 | 结果 |
|---|---:|
| 五帧总数 | 4, 3, 5, 5, 5 |
| 人工总数 | 3, 4, 4, 3, 5 |
| 总数 exact | 1 / 5 |
| Count MAE | 1.000 |
| 漏计 / 多计 | 1 / 4 |
| 调用 / token / wall | 91 / 291,099 / 1,166.5 s |

树在每一帧都打到 8 个节点上限，平均约 18 次调用、58k token、233 s/帧；
`south_1200` 单帧 313 s。它没有找回 `north_600` 的远端两节（3 vs 4），却在
`north_1200` 多 2、`south_600` 多 1。根区域提出、父子候选、跨节点相邻框三者
叠在一起，失败时很难定位到底哪一层出错。

### 下注结论

**当前形态淘汰。** 淘汰不是因为“递归听起来复杂”，而是因为实测成本约 A′ 的
2–3 倍，exact 反而从 4/5 降到 1/5。只有未来把节点数压到 3–4 个、并用固定根区域
替代自由提案后，才值得重新下注。

## 6. 路线 C：场景图 + 队列顺序

### 假设

先描述通道，再给每个物理车辆一个节点，显式输出 `lane_id`、`queue_index`、`part_of`。
如果模型能在关系层把“车头”和“挂车”连起来，计数就不需要靠框重叠猜。

### 实测证据

| 指标 | 结果 |
|---|---:|
| 五帧总数 | 2, 2, 4, 3, 4 |
| 人工总数 | 3, 4, 4, 3, 5 |
| 总数 exact | 2 / 5 |
| Count MAE | 0.800 |
| 漏计 / 多计 | 4 / 0 |
| 调用 / token / wall | 21 / 67,228 / 224.8 s |

它是最便宜的独立架构（约 4 次调用、13k token、45 s/帧），但反复漏掉远端队列：
`north_300` 少 1、`north_600` 少 2、`south_1200` 少 1。它没有“乱加”，更像是
把远端小目标当成背景。

### 下注结论

**不单独计数，保留关系层。** 下一步只用它的 `part_of` / `queue_index` 解决
`south_600` 的车头-挂车关系；候选来源仍用 A′ 的紧贴窗口。如果加入关系层后
不能把 `south_600` 从 5 降到 4，就删除这条线。

## 7. 路线 D：整帧后置审稿

### 假设

第一次整帧识别后，把编号框画回原图，再让模型独立重数并找漏检/重复/车型错误；
每个 missing 候选再单独裁剪复核。

### 实测证据

| 指标 | 结果 |
|---|---:|
| 五帧总数 | 2, 2, 4, 3, 5 |
| 人工总数 | 3, 4, 4, 3, 5 |
| 总数 exact | 3 / 5 |
| Count MAE | 0.600 |
| 漏计 / 多计 | 3 / 0 |
| 调用 / token / wall | 27 / 94,346 / 339.1 s |

它与整帧基线 `2,2,4,3,5` 完全相同：审稿没有找回 `north_300` / `north_600`
的远端车，也没有改变南机位。个别帧的 audit 找到了一个候选，但验证后又被拒绝；
这不是可重复的能力。

### 下注结论

**独立形态淘汰。** 审稿可以作为 A′ 之后的“漏检 veto”，但前提是它只能减少
已确认的候选，不能自己新增总数。它单独作为架构没有超过基线，成本却是基线的
4–5 倍。

## 8. 下一步实验（按优先级）

1. **20 帧回归 A′**：用人工 v2 的 10 个时刻 × 2 机位，固定全部参数，先不调提示词；
   报告 exact、MAE、漏计/多计、调用、token、wall。
2. **far 窗口三次独立采样 + 语义合并**：只对 far 窗口重复采样，不直接对总数投票；
   把三份候选的并集送给 A/B 语义判定，检查 `north_600` 两节货厢是否稳定出现。
3. **车头-挂车关系层**：只对 `south_600` 这种跨窗相邻框调用 `part_of` 判定，
   要求返回“同一辆车的车头与货厢/相邻两辆车”的证据；不能让几何直接合并。
4. **车型复核再设计**：当前 crop 仍会把上方邻车货厢带入；应把目标框高亮、
   邻车上下文标注为“非目标”，并单独统计 `unknown`。人工 v2 没有车型真值，
   不能在此之前报告车型准确率。
5. **稳定性和失败率**：每个架构至少重复 2 次，记录调用失败/超时；单次胜利不算能力。

## 9. 明确不声称的内容

- 不声称“五帧 4/5 就是 80% 生产准确率”；
- 不声称 20 帧回归已经通过；
- 不声称车型已正确；
- 不声称跨机位唯一车辆已解决；
- 不声称所有模型都可复现：本轮只有 Doubao 端点稳定可用，智谱图像请求失败，
  AIBox 的 `glm-5.3`/`glm-5.2` 调用不稳定。
